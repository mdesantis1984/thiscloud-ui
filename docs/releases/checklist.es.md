# Lista de publicación web

[English](checklist.md) · [Índice de documentación](../README.md) · [Versión e identidad de artefactos](versioning.es.md)

**Lista para una futura operación**, disponible solo en el repositorio; no autoriza una publicación. No ejecute operaciones sobre etiquetas, registros, despliegues ni hosts solo porque las pruebas locales pasen. Consulte la [guía de versiones](versioning.es.md) para identificar las fuentes de referencia; registre el propietario responsable, issue aprobado, revisión, versión y evidencia en cada etapa.

## 1. Preparar y revisar localmente

- [ ] Confirme el issue aprobado, alcance, responsable del cambio, versión e impacto en migración, soporte y notas de publicación. Actualice `README.md`, `CHANGELOG.md`, `MIGRATION.md`, `SUPPORT.md` del paquete y la documentación pertinente de API y consumo cuando corresponda; las guías de publicación de la raíz **no** se incluyen en el tarball web. Si una entrada existente de checksums contradice los nuevos bytes del paquete, deténgase: nunca sustituya la entrada ni bytes publicados bajo la misma versión.
- [ ] Desde la raíz del repositorio, compruebe los requisitos instalados y ejecute las comprobaciones específicas pertinentes, `pnpm check:web` **seguido de** `pnpm check:release`, `pnpm release:verify` y `git diff --check`. Las dos comprobaciones completas comparten resultados del catálogo y deben ejecutarse secuencialmente. `check:release` prepara el tarball y su checksum locales y las copias de descarga del catálogo; **no** publica. Registre el nombre del archivo, versión, checksum y resultados reales; inspeccione la documentación empaquetada e indique las comprobaciones omitidas. Ejecute las comprobaciones Flutter solo cuando corresponda y con sus propios requisitos.
- [ ] Revise la unidad de trabajo, límite de reversión, afirmaciones bilingües, riesgos y pruebas reales. Obtenga la aceptación explícita del propietario; ni un archivo preparado localmente ni una CI satisfactoria autorizan la publicación.

## 2. Promover la revisión aprobada

- [ ] Siga el flujo de issue aprobado, rama y PR hacia `develop`; autorice y revise por separado la promoción protegida `develop` → `main`. Compruebe nuevamente las protecciones vigentes y las pruebas requeridas contra la base real; ni la referencia local de seguimiento, ni una CI antigua, ni un PR anterior acreditan la integración. No omita protecciones, envíe cambios directamente a `main` ni introduzca implementación nueva en un PR de promoción.
- [ ] Antes de operar sobre etiquetas, apruebe por separado la versión exacta y el commit de `main`. El workflow del repositorio responde a una etiqueta `ui-web-v*` **enviada al remoto**: exige que `ui-web-v<version>` coincida con `packages/ui-web/package.json` en el commit etiquetado y que este sea ancestro de `main`. Enviar esa etiqueta puede iniciar la publicación; crearla o compilar localmente no equivale a ello. Deténgase si no se conocen ascendencia, identidad de etiqueta, publicaciones anteriores, permisos o autorización; nunca mueva una etiqueta publicada.

## 3. Publicar solo con autorización separada

- [ ] El workflow autorizado `.github/workflows/release.yml`, activado por etiqueta, se ejecuta en un runner privado: instala dependencias, ejecuta `check:web` y luego `check:release`, crea una publicación de GitHub en estado **draft** con `thiscloud-ui-web-<version>.tgz` y `.tgz.sha256`, envía a GHCR las etiquetas `:<tag>` y `:sha-<commit>` y después convierte la publicación en una versión preliminar publicada. Cada etapa puede fallar independientemente; un borrador, recursos cargados, una etiqueta de imagen o un paso correcto **no** prueban que la secuencia haya terminado.
- [ ] Vuelva a consultar la etiqueta y el commit exactos, conclusión del workflow, estado draft/prerelease, nombres y metadatos de los dos recursos e identidad del manifiesto autorizado del registro. Una etiqueta puede cambiar: resuelva y registre una referencia completa y verificada `ghcr.io/mdesantis1984/thiscloud-ui@sha256:<64 hex digits>` de la imagen real, independiente del SHA-256 del tarball. No deduzca ninguno de los dos digests de una etiqueta de imagen, un nombre de checksum ni una compilación local. Los metadatos de recursos de GitHub no acreditan por sí solos la disponibilidad de descarga.
- [ ] Con autorización separada para acceder a recursos externos, descargue el tarball publicado y su checksum en una ubicación controlada y compruebe de manera independiente los bytes del tarball contra el registro y el archivo de checksum; compruebe los bytes servidos por el catálogo y los enlaces públicos de documentación cuando ese servicio forme parte del alcance. Esta guía no ejecuta ni certifica esas solicitudes. Registre origen, hora, bytes y resultado reales; no se descargaron recursos ni se consultaron registros o endpoints públicos para redactar esta documentación.

## 4. Detenerse o derivar la recuperación

- [ ] Si fallan las pruebas, se reutiliza una versión con otros bytes, la etiqueta apunta a otro commit, falta autorización o solo existen un borrador o una publicación parcial en GHCR: **deténgase**, conserve la evidencia exacta e identifique lo ya publicado. No elimine automáticamente recursos, fuerce o mueva etiquetas, purgue imágenes, modifique entradas históricas del registro ni reintente suponiendo que la operación es atómica. Solicite al propietario un plan aprobado por separado para una versión nueva o la recuperación.
- [ ] El despliegue es una operación autorizada distinta: verifique el entorno destino, los digests completos de las imágenes actual y anterior, la identidad del artefacto del paquete y el operador antes de intervenir un servicio. Restaurar un digest anterior exige un procedimiento aprobado por separado y comprobaciones en vivo. Una versión preliminar publicada no equivale a un catálogo desplegado ni a una recuperación probada. Registre la comprobación posterior a la publicación y la revisión del propietario sin cerrar el issue solo por pruebas locales.
